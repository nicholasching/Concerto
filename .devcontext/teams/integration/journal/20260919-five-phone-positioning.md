## Findings, experiments and implemented behavior

- The baseline has five correctly decoded IDs, 2–6, but permanently vetoes 2 and 3 for track warnings. Inspection of the original image and instrumented associations shows rolling color/exposure changes generating one-frame screen fragments. These compete with the continuous phone track even though no independent phone crossed it. Device 2 also changes component area as the screen color changes.
- Initial v1.6 experiment recovered 4/5. The remaining collision flag came from a single-frame fragment with a temporarily disjoint bounding box. Collision evidence now requires an independently separated peer observed for at least three samples and 60 ms, or another complete preamble. Fragment births are compared against the corresponding older screen footprint, not a later partial component. Packet-interval collisions remain a veto; size/association warnings alone do not override a valid code.
- The user explicitly requested broader acceptance while work was ongoing. One bounded member-ID pass with an unreadable repeat is accepted and labeled; conflicting readable IDs, exact tag/header failure, nonmembers, duplicate identities/reflections and real collisions remain rejected/ambiguous. No timing, Hamming error bound, identity membership or transmitted-packet change. [Decision](../../../decisions/20260919-valid-code-acceptance.md).
- Both upload paths now carry optional frameLayout. Phone uploads default to from-stage; the admin also supplies this for old null-geometry receipts on Process, before creating the job. The worker uses actual rotated video dimensions and publishes the distinct frame-layout mode. Manual corners take precedence; old manifests without either declaration retain column-only behavior. This avoids silently relabeling existing results. Backend stale-geometry guards include orientation. [Decision](../../../decisions/20260919-automatic-frame-layout.md).
- Admin removes the requirement to mark corners before getting dots, labels automatic positions approximate, preserves editable direction/rotation/corners, and retains review/commit. Phone upload instructions state the camera direction. No dependency changes or edits to beatsync-source.
