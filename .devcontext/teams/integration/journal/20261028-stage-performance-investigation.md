## Source findings

- `CalibrationPanel.tsx` disables the created-run button for `busy`, zero/missing matching calibration `readyIds`, or `!clockReady()` on the **operator** browser. No quorum/fraction exists. Preparing normally selects currently connected, foreground, clock-ready phones. Music decoding and audio unlock are not calibration prerequisites.
- Backend arm independently requires a matching created run/preparation, at least one acknowledgement and sufficient future lead time. It sends the arm only to ready IDs. Projector aggregate sync is distinct from run-specific acknowledgements and does not report operator clock quality.
- Operator `clock.ts` constructs `ClockSync` without a profile, hence strict: 16 accepted pairs, minimum RTT <=40 ms (uncertainty <=20 ms), newest accepted pair <=3750 ms. Audience defaults internet: 16 pairs, minimum RTT <=300 ms, freshness <=10000 ms. Strict audience opt-in remains available.
- Both use minimum RTT over the last 16 accepted pairs, with 25 ms paired sends and <=5 ms mismatch between client-send/server-receive gaps. High queue jitter can reject pairs separately from RTT admission. `RESPONSE_TIMEOUT_MS=3750` also prunes outstanding probe correlations; it is distinct from the internet freshness policy.
- Unready/no-new-accepted-pair lifecycle restarts every 25+50=75 ms, two probes each cycle. Ready steady cadence is approximately 2.5–2.7425 seconds per pair. A stable path above admission limits keeps fast retries indefinitely. This is a potential congestion amplifier, not proof of the historical network bottleneck.
- Operator receives full telemetry snapshots at most twice/second on the same socket as clock replies and also polls HTTP once/second. Participant status can send twice/second and each receives a full own snapshot. Bulk stems share the public proxy/network. These are candidates for measurement, not established causes of the Railway percentiles.
- `device.status` with false foreground/clock readiness excludes a prepared phone from the calibration barrier. A later ready status does not restore its ACK. The participant only sends a positive `calibration.ready` on `CalibrationSession.onPrepare`; sync recovery does not call it again. Preparation is broadcast once, and participant snapshots do not replay its plan. Thus sync recovery or reconnect can leave a frozen run with zero ready ACKs even when many phones subsequently report clock ready. This is a second source-supported explanation for the disabled control.
- Admin `safeFetch` has no request timeout; a hanging operation can hold the panel's `busy` flag. Its HTTP snapshot polling uses `setInterval` without an in-flight guard, so slow responses can overlap. Neither fact establishes that this happened on stage.
- Calibration requests start four seconds ahead; backend requires 1500 ms remaining at receipt. >2500 ms operator-command transit can yield `INSUFFICIENT_LEAD_TIME` after clicking. This cannot directly explain an already-disabled button. Two-second playback commands have only 500 ms transit margin under current policy.

## BeatSync and directional-delay follow-up

User asked whether BeatSync uses the same mechanism and whether directional latency can improve accuracy. Re-read the supplied reference's `utils/ntp.ts`, `hooks/useNtpHeartbeat.ts`, `store/global.tsx`, server `ntpRequest.ts` and shared constants. Both implementations use four timestamps, minimum-RTT selection over 16 accepted paired measurements, 25 ms probe gaps and 5 ms gap tolerance. **The reference does not use our 40/300 ms readiness gates**: `global.tsx:1066` latches synced after 16 results; `:1015` only warns when average RTT exceeds 750 ms. Earlier conversational wording about an inherited strict profile must be understood/corrected as our estimator default, not a BeatSync admission requirement.

Checked primary references: [RFC 7679 sections 3.5/3.7.1](https://www.rfc-editor.org/rfc/rfc7679.html#section-3.7.1), [RFC 5905](https://www.rfc-editor.org/rfc/rfc5905.html), [Web Audio getOutputTimestamp](https://www.w3.org/TR/webaudio/#dom-audiocontext-getoutputtimestamp). One-way delay measurement requires accounting for clock disagreement; unsynchronized endpoint timestamps alone cannot identify fixed path asymmetry separately from clock offset. More low-delay samples and clock-drift modeling can improve estimates but do not identify arbitrary constant asymmetry. An independent common clock/reference changes that problem but needs additional infrastructure. Local output-clock mapping is separate from network directionality; current `packages/audio/src/timing.ts` already uses valid output timestamps with a latency-aware fallback. No source/reference changes or additional test runs were needed for this explanation.
