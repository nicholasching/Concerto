## Goal

Stage 01 slice 4: get large files onto the server without melting the control process, hand them to
Team 3's decoder across a process boundary, and commit the result into the audience map only after
checking it describes the run we asked for.

## The properties that matter here

1. **The control process stays responsive.** Three 4K clips must stream to disk while 1,500 phones
   hold sockets. Nothing reads a whole video into memory, and video decoding happens in another
   process entirely.
2. **A filename from the network is never a command.** The worker is given server-resolved paths
   and is spawned with an argument list, never a shell string.
3. **A result has to prove which run it belongs to** before it can touch the map. Wrong run, wrong
   hashes, wrong session or an older run arriving late are all rejections, not merges.
4. **Unknown stays unknown.** A device the decoder could not place is recorded as unseen or
   ambiguous. It never becomes a position.

## Subplot: slice 4, in four reviewable steps

Contracts already fix the shapes: `CalibrationCreateRequest`, `CalibrationArmRequest`,
`CreateJobRequest`, `CommitMapRequest`, `JobProgress`, `CalibrationManifest`, `OtcResult`,
`CameraInput`, `Location`, `AudienceMap`, `Track`. No schema change is proposed.

### Step 4A - audio assets

`POST /api/assets` streams an uploaded audio file to disk, hashes it while it streams, and
registers a `Track` with its real byte size and SHA-256. `GET /api/assets/:trackId` serves it back
with cacheable headers. The registered hash is what phones compare against, so a corrupted or
truncated upload is caught before a show references it.

Tests: the stored hash matches the bytes; a truncated upload is rejected rather than registered;
registration is idempotent by command ID; the served file matches what was uploaded; a track
referenced by a saved show cannot be silently replaced.

### Step 4B - calibration runs and camera uploads

`POST /api/calibrations` freezes a run: participant IDs, palette and versions, run tag, and a
`runId`. Only one active run at a time. `POST /api/calibrations/:runId/arm` reuses the existing
barrier machinery to schedule a start at least the configured lead time ahead, after phones
acknowledge `calibration.prepare`.

`POST /api/calibrations/:runId/uploads` streams one camera file to a server-chosen path, hashes it,
and records camera ID, primary column and capture metadata. The client's filename is stored as a
label and never used as a path.

Tests: a second concurrent run is refused; a run tag is not reused within a session; an upload for
an unknown run is refused; the stored path is server-generated regardless of the submitted
filename, including names containing traversal or shell characters; hashes are frozen once the
upload completes.

### Step 4C - the worker boundary

`POST /api/calibrations/:runId/jobs` builds a `CalibrationManifest` from the frozen uploads and
enqueues one job. `GET /api/jobs/:jobId` reports `JobProgress`.

The adapter spawns a child process with an argument array, parses structured progress from stdout
and keeps stderr as diagnostics. The server owns queueing (one job at a time), a timeout, and
cancellation; a job that exits non-zero, times out, or emits an unparseable result fails with its
diagnostics preserved rather than being retried silently.

A fake worker is injected for tests. The real command is configuration, so switching to Team 3's
CLI is a setting rather than a code change.

Tests: a manifest names every frozen upload with its hash; a second job is queued rather than run
concurrently; a timeout kills the child and reports failure; a non-zero exit preserves stderr; a
malformed result is rejected; a cancelled job does not later commit; a filename containing shell
metacharacters reaches the worker as one literal argument.

### Step 4D - map commit

`POST /api/calibrations/:runId/commit-map` validates the result's session, run and input hashes
against what the server actually sent, checks `expectedMapRevision`, then replaces locations for
the run's target devices only. Devices the run targeted but could not place become unseen or
ambiguous. Devices outside the run keep their previous positions. A result from an older run cannot
overwrite newer locations.

Committing bumps `mapRevision`, which makes selections built against the old map stale, and the
existing check in `POST /api/assignments` starts refusing them. The committed map is durable.

Tests: identity mismatch is refused; a stale `expectedMapRevision` is refused; targets are replaced
and non-targets retained; a failed target becomes unseen rather than `(0,0)`; an older run is
refused after a newer commit; an assignment built against the previous map is refused afterwards;
the map survives a restart.

## Open decisions for the lead

1. **Where uploaded files live, and when they are deleted.** Three 4K clips per run is roughly a
   gigabyte, and a rehearsal day is many runs. Proposal: a server-owned directory outside Git,
   configurable, with files kept until the run's map is committed or the run is explicitly
   discarded, and a documented manual cleanup. Automatic deletion of the only copy of a recording
   during a rehearsal seems worse than running out of disk with a warning.
2. **What happens to an in-flight job when the server restarts.** Proposal: it is marked failed
   rather than resumed. The committed map is durable; a half-finished decode is not, and silently
   resuming work whose child process died would report progress nobody is making.

## Decisions taken by the lead

1. **Uploaded files are kept until their run's map is committed or the run is discarded**, in a
   server-owned directory outside Git, with manual cleanup documented. Deleting the only copy of a
   recording automatically during a rehearsal is worse than running out of disk with a warning.
2. **A job in flight when the server restarts is marked failed, not resumed.** Its child process is
   gone; resuming would report progress nobody is making. The committed map is durable, so the cost
   of re-running is the decode time, not the calibration.

## Progress

- Subplot approved. Step 4A implemented. Steps 4B, 4C and 4D not started.

### Step 4A implemented

- `backend/src/assets.ts`: `AssetStore` streams a body to disk while hashing it in the same pass,
  writes under a `.partial` name and renames only when the stream ends, so an interrupted upload
  can never be mistaken for a complete asset.
- `POST /api/assets` (operator-only) registers a `Track`; `GET /api/assets/:trackId` serves it with
  immutable cache headers.

Decisions taken while implementing:

1. **Metadata travels in the query string and the body stays a raw stream.** Multipart parsing in
   Hono buffers the whole body in memory, which is exactly what rules section 10 forbids. This
   matters far more for 4B's 4K video than for audio, and one mechanism for both is simpler.
2. **Duration, sample rate and channel count are declared, not verified.** Confirming them means
   decoding audio in the control process, which is the CPU work that belongs elsewhere. Size and
   hash *are* measured, and the hash is what a phone checks. Documented in the handoff so nobody
   mistakes the declared values for verified ones.
3. **Track IDs are server-assigned UUIDs**, so an upload can never overwrite a track a saved show
   already references, and no registry lookup is needed to serve a file.
4. **`GET /api/assets/:trackId` is unauthenticated.** Every participant needs the audio, the id is
   unguessable, and this is the route that should move to a static host before the event. The id
   from the URL is matched against a strict pattern before any path is built from it.
5. **A short upload is rejected rather than registered.** A truncated file would put a hash into a
   show that no phone could ever match, and the failure would surface as silent phones at showtime.

### Checks run

- `bun run gate:sync` - PASS, 123 tests across backend, sync and testkit.
- Live against the running server with a 3 MB random file: the returned SHA-256 matched `shasum`
  computed independently on the source file; the served bytes were byte-identical under `cmp`; a
  declared size larger than the body returned 400 and left nothing on disk; a traversal attempt in
  the URL returned 404; an upload without the operator secret returned 401. One file in the store
  afterwards, not two.

### Failures encountered

- A scripted edit duplicated the new dependency in four test harnesses and skipped a fifth, and
  `tsc` caught it. Repaired each file individually rather than with another blind replace.
- The same scripted edit wrote a literal NUL byte into a test file where the source needed the
  escape ` `. Tests passed either way, which is what made it worth checking: a control
  character sitting invisibly in a source file is the kind of thing that survives review and breaks
  a tool later. Replaced with the escape and confirmed zero NUL bytes remain.
