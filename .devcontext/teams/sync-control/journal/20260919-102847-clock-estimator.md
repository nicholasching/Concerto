## Goal

Stage 01 slice 1: a per-session coded-probe clock estimator with an injected clock, plus the
server timestamp reply path, so two independent clock clients can converge without React,
audio, or any other team's unmerged code.

## Assumptions

1. The frozen wire contract is authoritative: `clock.probe` carries `{probeGroupId, probeGroupIndex, t0}`
   and `clock.reply` carries `{probeGroupId, probeGroupIndex, t0, t1, t2}`, both inside the
   `SessionIdentity` envelope (`protocolVersion`, `sessionId`, `serverEpoch`, `messageId`).
   `t3` is recorded locally by the client and never travels on the wire.
   No contract change is proposed in this slice; `packages/contracts/` is captain-owned.
2. `serverEpoch` is a string ID in the contract, so epoch change is detected by inequality,
   not ordering. A reply whose epoch differs from the session's current epoch invalidates
   every prior measurement rather than being merged.
3. Identity/authentication arrives in slice 2. This slice's socket accepts `clock.probe` only
   and answers `clock.reply`; it allocates no device IDs and mutates no concert state.
4. The 20 ms clock-quality eligibility threshold from masterplan section 6 is a configured
   starting value to be tuned from evidence, not a measured result.

### Step 1A - per-session estimator in `packages/sync/`

Extract from `beatsync-source/apps/client/src/utils/ntp.ts`
(SHA-256 `40bef103bb563e8eddcdf8395d18d15bfbcd3eedef24f1e58110bfe634456341`, already recorded
in the provenance ledger as pending Team 1).

Retained behavior, unchanged:

- `clockOffset = ((t1 - t0) + (t2 - t3)) / 2`, server minus client.
- `roundTripDelay = (t3 - t0) - (t2 - t1)`.
- Coded probe pairs: buffer index 0; on index 1 with a matching group ID compare the client
  inter-departure gap against the server inter-arrival gap, accept the pair when the drift is
  within tolerance, and keep the lower-RTT member of an accepted pair.
- Min-RTT offset selection across the retained measurement window.
- Constants from `beatsync-source/packages/shared/constants.ts`
  (SHA-256 `cf9cd4bea25cc9fb7c3b6541ab640c9fa7ed3d00b3d76530150abdcd5889818d`):
  `PROBE_GAP_MS` 25, `PROBE_GAP_TOLERANCE_MS` 5, `MAX_MEASUREMENTS` 16,
  `INITIAL_INTERVAL_MS` 50, `STEADY_STATE_INTERVAL_MS` 2500, `RESPONSE_TIMEOUT_MS` 3750.

Deliberate differences, each with its reason:

| Difference | Reason |
| --- | --- |

| Adds `serverEpoch` tracking | Masterplan section 4: an epoch change invalidates prior timing; BeatSync has no epoch concept |
| Adds sample age and quality reporting | Stage brief slice 1 and the `ClockQuality` seam already in `packages/sync/src/index.ts` |
| React heartbeat hook is not ported | `useNtpHeartbeat.ts` is React-bound; the reprobe schedule becomes a transport-agnostic policy that Team 2's client and the load harness both drive |

### Step 1B - fast timestamp reply path in `backend/`

Add a WebSocket route beside the existing Hono health shell. It parses the envelope with
`ClientMessage`, and for `clock.probe` replies with `clock.reply` carrying `t1` sampled at
receipt and `t2` sampled immediately before send, with the session's `serverEpoch` and the
echoed probe group fields. No other message type is accepted yet; anything else returns the
structured `NOT_IMPLEMENTED` error rather than being silently dropped. The 501 catch-all for
unimplemented HTTP routes stays as it is.

`serverMs` comes from a monotonic-backed server clock created once per process; the epoch ID is
minted at startup, so a restart produces a new epoch and invalidates prior schedules by
construction.

Tests: probe/reply round trip echoes the group fields; `t1 <= t2`; a malformed envelope or an
unsupported type produces a structured error; a reply's epoch matches the server's current epoch.
Then an in-process test drives two independent estimator instances against the real handler over
a scripted transport and asserts both converge to the injected truth within the deterministic
symmetric-delay target.

Verification: `bun test backend/tests packages/sync/tests`, then `bun run gate:sync`.

### Decisions taken while implementing

1. A probe carrying a stale `serverEpoch` is answered rather than rejected. The reply is how a
   reconnecting client learns the current epoch, and the estimator resets its measurements when it
   sees a new one. A mismatched `sessionId` is still a hard error. Consumers must therefore treat
   `clock.reply.serverEpoch` as authoritative and never assume their cached epoch is current.
   This uses the frozen contract as written; no schema change was needed.
2. An unmatched second probe does not discard the buffered first probe. This is the source's
   behavior and it is safe, because pairing requires an exact group-ID match; the test now states
   the property directly instead of asserting the buffer is cleared.
3. Readiness is recomputed on every call rather than latched once, so it degrades when samples go
   stale. The source latched it. Recorded as a deliberate difference in the provenance ledger.
