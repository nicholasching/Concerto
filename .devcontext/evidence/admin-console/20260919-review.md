## Priority findings

### R1 — P1: Schedule transport and mix commands in the future

`admin-frontend/src/components/PerformPanel.tsx:17,32,42` uses the last snapshot's `serverMs` and passes zero delay for every transport/mix operation. By the time the command reaches the server, that timestamp is in the past. A conforming server must reject or reschedule it; immediate application cannot implement the planned preparation/readiness/future-start workflow. The UI probe invokes the actual Play and gain handlers and captures `effectiveServerMs: 100000` for a snapshot sampled at 100000. Assignment Undo uses the same zero-delay problem (`AssignPanel.tsx:39`).

Use the shared clock boundary, readiness/preparation state and an agreed future lead time. Verify delayed delivery, pending versus effective state, and a common playhead before enabling controls.

### R2 — P1: Confirm a command by its identity and actual result

`admin-frontend/src/lib/adapter.ts:64-69` confirms every pending command whenever the global revision advances. `:77-82` also leaves network failures pending. Reproduction: an assignment that never reaches the server changes from pending to confirmed when an unrelated snapshot revision changes from 10 to 11. A future assignment remains in `snapshot.pendingActions` for another 60 seconds while the adapter labels it confirmed. This violates the explicit no-premature-success requirement.

Track sent/accepted/scheduled/effective/error states from the validated response and matching command/domain state. Handle thrown requests and epoch changes explicitly; an unrelated revision is insufficient evidence.

### R3 — P1: Preserve the revision captured with the selection

`admin-frontend/src/components/MapPanel.tsx:76` discards `DeviceSelection.mapRevision`; `AssignPanel.tsx:27` attaches the latest map revision at submission. Reproduction: select IDs on revision 1, replace the map with revision 2 and moved coordinates, then Assign. The old IDs are sent with revision 2, bypassing the intended stale-map rejection.

Keep the complete selection object, invalidate/reconfirm it on map or session changes, and submit its captured revision. Test a map update between drag and submit.

### R4 — P1: Use inverse drawing coordinates for selection

`admin-frontend/src/components/MapPanel.tsx:31-33` normalizes mouse positions over the whole canvas, but `:47` draws dots inside a padded rectangle (`20 + x*860`, `30 + y*310`). Selection and display therefore refer to different locations. The actual handler probe draws an 8px box around the visible device-0 dot at canvas `(106,61)` for map `(.1,.1)` and gets zero selected devices.

Share one map-to-canvas transform and its inverse, including CSS scaling and padding. Test visible boundary dots and narrow selections at the front/back/edges.

### R5 — P1: Replace hardcoded calibration participants with eligible live IDs

`admin-frontend/src/components/CalibrationPanel.tsx:27-29` always requests IDs 0 through 29. Sessions smaller than 30 include nonexistent devices; larger/non-contiguous sessions exclude valid participants. The plan requires an authoritative eligible/target subset. Pass that subset and expose ready/excluded counts; test both small and >30-device sessions.

### R6 — P1: Implement the prepare/ready/arm transition

`admin-frontend/src/components/CalibrationPanel.tsx:29-30` creates a plan and proceeds to uploads, with no preparation/readiness UI or scheduled arm. Searching `armCalibration` in the application finds only its unused definition at `adapter.ts:102`. Under the frozen protocol, creating a plan does not start flashing. Add the readiness and explicit future-arm step, camera-recording instructions and countdown before the capture/upload workflow.

### R7 — P1: Review the candidate map before enabling commit

`admin-frontend/src/components/CalibrationPanel.tsx:65-66,85-86,125` retains only progress and enables Commit on completion. The Review tab (`page.tsx:76`) displays the existing committed map. No UI consumes the proposed `OtcResult`, its observations, camera diagnostics or rejected cases. The operator cannot inspect the map about to replace the live map.

Fetch and validate the candidate, show evidence/orientation/registration and unresolved devices, and bind explicit approval to that job/run/map revision before committing.

### R8 — P1: Agree calibration/job response contracts with the producer

`admin-frontend/src/lib/adapter.ts:100,117` casts HTTP results to invented shapes with `runId/runTag` and `jobId`. Frozen `.devcontext/schema/protocol.md` specifies `CommandAccepted` for successful HTTP mutations; that executable schema lacks those fields. The probe returns valid `CommandAccepted` results and the adapter gives the UI undefined run/job identities. There is no accepted ADR defining these additional result shapes.

Team 1/captain and Team 4 must agree the resource/preparation handoff, then consume validated schemas/events. This is an unresolved integration boundary, not permission to silently broaden shared contracts. The snapshot URL is also hardcoded to session `demo`, and operator credential/session selection wiring remains unverified.
